# CC프롬프트4_클라 피드백

약 180개, 클라 세션 로그. 여기 교정본이 실제로 쓰인 흔적이 있어서, 처방이 먹혔는지도 같이 확인할 수 있는 배치다.

---

## 교정본의 실제 성적

### 먹힌 것

탄약 복구 프롬프트는 거의 그대로 나갔고, 다음 턴이 `B안으로 진행할게` 한 줄로 끝났다. `.proto` 주석 정책 교정본도 인계용 구분 항목까지 살려서 사용됐고, `ItemDBHelper` 건은 "어디에 넣을지"가 빠져 있다는 지적을 `CLAUDE.md에 추가하려고 해`로 직접 채웠다.

### 빗나간 것

명중 누락 진단이 그렇다. 관문별 카운터를 심는 계측 계획을 권했는데, 실제로는 이렇게 진행됐다.

> "첫번째발 조차 맞지 않았다는 점이 걸려. 나는 반동 제어를 하면서 사격했고 적 개체를 중앙에 두고 사격했어. raycast궤적을 확인해 봐야 될 것 같아."

그리고 시각화 한 번으로 문제 두 개를 다 찾았다. **첫 발조차 안 맞는다면 확률적 손실이 아니라 기하 문제이므로 계측이 아니라 궤적을 봐야 한다** — 이 판단이 처방보다 빨랐다. 심으라고 한 카운터는 결국 다 지웠다.

교정본이 문제 규모에 비해 과했다. 앞으로 계측 계획을 권할 때는 "손실이 확률적으로 흩어져 있을 때"로 조건을 붙인다.

## 새로 자리잡은 것

### 1. 제안에 근거를 요구하는 빈도가 확 늘었다

> "히트박스 튜닝의 경우, 지금껏 여러 피격실험을 해보았는데, 이상한 점을 느끼지 못했어. 이 작업의 필요성에 대해 먼저 설명해줄래?"
>
> "계층 규격을 새 문서로 이관하는 것으로서 판단한 이유를 먼저 듣고싶어."
>
> "현재 문맥에서 플러시가 뭐지?" / "모듈 문서란 무엇을 말하는거지?" / "어떤 타이머를 말하는거지?"

이번 배치에서 가장 좋은 변화다. 특히 뒤의 셋은 **모르는 용어를 넘기지 않는 습관**인데, LLM이 만든 용어를 그대로 받아 쓰다 보면 존재하지 않는 개념을 둘이서 공유하게 된다.

### 2. 검증 결과를 구조화해서 보고한다

> "1. 컴파일 문제없음 2. 빈 탄창에서의 발사 시의 효과음 정상 출력 확인 3. 무기교체, 발사, 새로운 탄약보급의 여파 등으로 IngameWeaponUI의 변화가 적절한 시기에 잘 이루어짐을 확인"

이전 배치에서 "검증이 병목"이라고 했던 부분이 해소됐다. 2인 접속 테스트 결과를 항목별로 확인하고 넘어가는 게 여러 번 나온다.

## 이번 배치의 최대 발견: 문서 정리가 상시 작업이 됐다

한 배치 안에서 문서를 걷어내는 작업이 **여섯 건** 나온다.

- `progress.md`의 `##메모` 섹션 제거
- 각 모듈 CLAUDE.md 비대화
- `.proto` 주석에서 처리 과정 제거
- `server-sync-todo.md` 삭제
- 콜라이더·발사 실측표 제거
- "문서에 그런 뉘앙스로 쓰여있다면 제거해줘"

각각은 정당한 정리인데, 여섯 번 반복된다는 건 **생성 쪽에 제약이 없다**는 뜻이다. 원인은 이 문장에 있다.

> "각 모듈의 CLAUDE.md 파일이 비대해지는 경향이 있어. 어떤 경위를 통해서 이렇게 작성되었는지에 대한, 특정 코드에 대한 히스토리가 필요이상으로 세부적으로 적혀있다고 판단되."

`문서화해줘`라고만 하면 경위와 히스토리가 들어간다. 그게 기본 동작이다. 지금은 **넣지 말아야 할 것을 매번 사후에 지우는 셈**이고, 지울 때마다 판단 비용이 든다.

`.proto`에는 이미 정책을 세웠다 — "어느 상황에 쓰이는 패킷인지 한 줄, 처리 과정은 안 씀". 같은 형식을 나머지 문서에도 한 번에 정하면 이 반복이 끝난다.

루트 CLAUDE.md에 넣을 것:

```
[문서 작성 규칙]
모든 문서는 목적과 금지 항목을 상단에 명시한다.
- CLAUDE.md: 그 모듈에서 작업할 때 반드시 알아야 할 규칙과 구조.
  금지 — 특정 코드가 그렇게 작성된 경위, 변경 이력, 실측 데이터.
- progress.md: 최근 진행 사항 몇 건과 앞으로 진행할 사항.
  금지 — 설계 근거, 미해결 논의, 실측표.
- External_Protocol.proto: 각 패킷의 사용 상황 한 줄.
  금지 — 수신 후 처리 흐름.
문서를 새로 만들거나 확장할 때, 위 금지 항목에 해당하면 넣지 말고 나에게 물어본다.
```

핵심은 **금지 항목**이다. 목적만 적으면 해석 여지가 남고, 결국 또 채워진다.

## `.proto` 변경 타이밍이 통제되지 않는다

> "기존의 계획을 파기해줘. 다시한번 External_Protocol에 변화 사항이 있었어."

클라 세션이 `.proto` 변경분을 보고 계획을 세우는 중에 파일이 또 바뀌어서, **계획이 두 번 버려졌다.** 이 배치에서 `.proto` 변화 추적 요청이 다섯 번 나온다.

이전에 `.proto` 수정 권한을 어느 세션이 갖는지 정하라고 했는데, 아직 미정 상태로 보인다. 권한 문제라기보다 **변경 시점** 문제다.

> 실용적인 선: 서버 세션에서 `.proto`를 고친 직후에는 클라 세션에 계획을 요청하지 않기. 서버 쪽 변경이 한 덩어리로 끝난 시점에 한 번만 추적 요청.

지금은 서버 작업 중간중간에 클라 세션이 따라가려다 헛돌고 있다.

## 삭제 프롬프트의 기준

> "시각화를 통해 전체적인 문제를 파악했어. 이번 세션에서 작업한 모든 임시 코드를 지워줘."
>
> "이제 server-sync-todo.md 파일이 없어져도 된다고 생각해."

둘 다 목록 확인 없이 바로 삭제다. 두 번째가 특히 걸리는데, 인계 목적으로 만든 파일이라 **내용이 소비됐는지 확인 없이 지우면 반대편 세션이 받아야 할 것이 사라진다.**

길이로 나눌 게 아니라 **되돌릴 수 있는지**로 나누면 된다. `삭제해줘` / `지워줘` / `파기해줘`가 들어간 프롬프트에만 한 줄 붙이는 것으로 충분하다.

```
대상 목록을 먼저 보여주고 멈춰줘. 내가 확인하고 지목할게.
```

## 짧아진 것은 옳다

로그 뒷부분으로 갈수록 프롬프트가 다시 짧아진다.

> "점프 행동에 잔여 스태미나 12를 요구하려고 해."
>
> "달리기 발소리 재생 타이머를 1f/3f 에서 0.25f 로 변경하려고 해."
>
> "총구 화염은 적용하지 않을거야. TODO항목은 완료야."

이건 후퇴가 아니라 **올바른 조정이다.** 값 하나 바꾸는 데 완료 판정 기준과 파일:줄 요구를 붙이면 그 자체가 낭비다. 앞서 제시한 템플릿은 되돌리기 어렵거나 범위가 불확실한 작업용이고, 이런 건 짧은 게 맞다. 매번 붙여야 하는 것이 아니다.

한편 스태미나 명세처럼 요구사항이 여럿인 건은 여전히 번호를 매겨 쓰고 있다. 구분이 이미 잘 되고 있다.

## 정리

프롬프트 수준에서는 더 손볼 게 많지 않다. 남은 비용은 **문서 생성 규칙**과 **두 세션의 `.proto` 변경 타이밍** — 둘 다 프롬프트 밖이다.
